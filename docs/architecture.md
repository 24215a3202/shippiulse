# ShipPulse architecture

## Phase 1 foundation

ShipPulse is a JavaScript npm-workspaces monorepo. The React/Vite web app runs separately from the Express API during local development. The API owns all data access; PostgreSQL is the system of record, Drizzle defines the schema and runs SQL migrations, and Redis is the shared store for later background work. PostGIS is added with the geospatial phase. No service is containerized.

```text
Browser (React + Vite :5173)
        │ HTTP / JSON
Express API (:3001) ─── PostgreSQL 18 (:5432)
        └────────────── Redis (:6379)
```

The API health endpoint checks PostgreSQL and Redis and returns HTTP 503 with per-service status if either dependency is unavailable. The web interface includes authentication, organization team management, driver profiles, fleet registration, driver-to-vehicle assignment, and shipment operations.

## Tenant data foundation

Organizations and users are tenant-owned tables. User rows carry a required organization foreign key and a unique `(organization_id, email)` index. Registration creates an organization and its first administrator in one transaction. Authentication resolves membership from PostgreSQL on each protected request and checks the stored user and organization status; the organization ID in a signed token must match the user's stored membership. Refresh-token families and password-reset tokens are stored only as SHA-256 digests. The Vite `/api` proxy keeps local cookie authentication on the same site.

## Phase 3 team and fleet

Driver profiles extend organization-owned user accounts with license and contact information. Vehicles are organization-owned and use a nullable current driver assignment. Database uniqueness rules prevent duplicate vehicle registrations within an organization and prevent one driver from being attached to multiple vehicles. API handlers verify that an assigned driver is active, belongs to the signed-in organization, and has a driver profile. Deactivating a driver releases their vehicle assignment.

## Phase 4 shipment workflows

Shipments, intermediate stops, and shipment events are organization-scoped. Tracking IDs are generated by the API. State changes follow an explicit transition map; dispatch assignment is accepted only for active organization drivers and vehicles, and a driver or vehicle can have only one active shipment at a time. PostgreSQL partial unique indexes backstop that rule. Every create, detail edit, assignment, and status change appends an event within the same transaction. Database triggers reject updates and deletes on shipment events.

## Phase 5 GPS tracking

Location updates are append-only records associated with an organization, shipment, vehicle, and driver. Device updates require an authenticated driver session and an active matching assignment. An organization-scoped event ID makes ingestion idempotent. The API stores valid out-of-order points for history without allowing them to replace a newer latest position; updates older than 24 hours or over five minutes in the future are rejected. Freshness is derived from the newest recorded timestamp. A development-only simulator marks every generated point with the `SIMULATOR` source.

## Phase 6 live tracking

Socket.IO shares the API HTTP server. Every connection authenticates its HttpOnly access cookie against the current database session and is periodically revalidated. Dispatch, admin, and viewer clients may join only their organization room; driver clients join only rooms for their assigned shipments. Server-only broadcasts publish shipment and location changes after the database transaction commits. The tracking screen updates the MapLibre GeoJSON source from those authorized events and keeps the OpenStreetMap attribution visible.

## Phase 7 geospatial operations

PostGIS stores geofence polygons, route lines, and stop points in SRID 4326. Circle radii and route/vehicle distances use geography calculations in meters. GiST indexes support spatial filtering. Accepted GPS points compare against active fences and the shipment's latest ordered route version in the same database transaction, recording geofence transitions, waypoint arrivals/departures, linked shipment-stop progress, and shipment timeline entries. Out-of-order points remain in GPS history without advancing spatial state. Only device points contribute to actual route distance; simulator events are visibly marked. Route versions preserve their manually supplied waypoint order and use straight-line segments; no road routing or traffic optimization is claimed. Migration 0005_geospatial.sql requires the PostGIS server extension to be installed first.

## Phase 8 exception engine

The API process periodically evaluates active shipments against configurable delivery, pickup, GPS, vehicle, route, and stop thresholds. A PostgreSQL advisory lock serializes scans across API instances. Each continuously active condition maps to one open exception record; a partial unique index backs up that idempotency rule. Scan cycles update `last_seen_at`, emit Socket.IO events for new and changed records, and resolve open exceptions when the condition clears. Operator actions support acknowledgment, assignment, resolution, and dismissal, with resolution notes retained. Route deviation and missed-stop checks require the Phase 7 spatial tables and PostGIS extension.

## Phase 9 notifications and analytics

The API queues notification fan-out in BullMQ after committed shipment, assignment, geofence, stop, exception, and exception-escalation events. A separate Node worker persists recipient-specific notifications with idempotency keys and exponential retries, then publishes to Redis Pub/Sub. The API bridges those persisted events to authenticated Socket.IO user rooms. Notification reads and read-state updates scope by both organization and recipient. Analytics APIs aggregate shipment and shipment-event records with server-side tenant and filter predicates; the React dashboard renders those results in KPI cards, volume charts, and driver/vehicle tables.
